⚠️ PHASE 0 — اكتشاف المجالات مع الأمن في الاعتبار
مجالات الأعمال مع تحليل التهديدات:
1. مجال الحقوق (Rights Domain) - CRITICAL RISK
yaml
الأصول الحساسة:
• حسابات العمولات المالية
• قواعد العمولات
• سجلات الاستحقاق التاريخية

أسطح الهجوم:
• التلاعب في قواعد العمولات
• تعديل الحقوق المحسوبة
• الوصول غير المصرح للحسابات

سيناريوهات إساءة الاستخدام:
1. موظف يعدل قواعد عمولاته الخاصة
2. مدير يحسب عمولات زائدة للموالين له
3. هجوم داخل النظام يغير حسابات مالية

تصنيف حساسية البيانات:
• قواعد العمولات: Financial-Critical
• حسابات الحقوق: Financial-Critical
• سجلات الحساب: Confidential
2. مجال الإنجاز (Achievement Domain) - HIGH RISK
yaml
الأصول الحساسة:
• أدلة إنجاز المهام
• شهادات الإتمام
• ملفات الجودة

أسطح الهجوم:
• تزوير أدلة الإنجاز
• تعديل شهادات الإتمام
• الوصول لملفات حساسة

تصنيف حساسية البيانات:
• أدلة العملاء: Confidential
• ملفات الشركة: Confidential
• تقييمات الجودة: Internal
3. مجال التحقق (Verification Domain) - CRITICAL RISK
yaml
الأصول الحساسة:
• إثباتات الدفع المالية
• سجلات التحقق البنكية
• نتائج مطابقة المعاملات

أسطح الهجوم:
• تزوير إثباتات الدفع
• التلاعب في نتائج التحقق
• تسريب معلومات مالية

تصنيف حساسية البيانات:
• إثباتات الدفع: Financial-Critical
• كشوف الحسابات: Confidential
• نتائج التحقق: Confidential
4. مجال التسوية (Settlement Domain) - HIGH RISK
yaml
الأصول الحساسة:
• سجلات النزاعات
• قرارات التحكيم
• درجات السمعة

أسطح الهجوم:
• التلاعب في قرارات التحكيم
• تعديل درجات السمعة
• تسريب معلومات النزاعات

تصنيف حساسية البيانات:
• قرارات التحكيم: Confidential
• أدلة النزاعات: Confidential
• درجات السمعة: Internal
5. مجال الهوية (Identity Domain) - CRITICAL RISK
yaml
الأصول الحساسة:
• حسابات المستخدمين
• مفاتيح الجلسات
• سجلات الصلاحيات

أسطح الهجوم:
• اختراق الحسابات
• تسريب مفاتيح الجلسات
• التصعيد غير المصرح للصلاحيات

تصنيف حساسية البيانات:
• بيانات تسجيل الدخول: Financial-Critical
• مفاتيح الجلسات: Confidential
• سجلات الصلاحيات: Confidential

🏗️ PHASE 1 — سياقات محمية بحدود أمنية
1. سياق الحقوق المحمي (Rights Protected Context)
yaml
المسؤولية الأمنية:
• حماية حسابات العمولات المالية
• ضمان عدم التلاعب في القواعد
• تسجيل كافة التغيرات المالية

حدود الثقة:
• لا ثقة ضمنية مع أي سياق آخر
• كل طلب مصادق عليه بشكل كامل

طريقة المصادقة:
• JWT مع claims محددة
• Tenant ID إجباري في كل طلب
• User ID + Role في payload

نموذج التخويل:
• Hybrid RBAC + ABAC:
  - RBAC: الأدوار (Owner, Manager, Employee)
  - ABAC: سمات (Department, Commission Limit, Time)

الأسرار المملوكة:
• مفاتيح تشفير لحسابات الحقوق
• مفاتيح توقيع للمعاملات المالية
• مفاتيح لفك تشفير القواعد

نقاط الدخول المسموحة فقط:
1. POST /rights/calculate (لخدمة الإنجازات فقط)
2. GET /rights/{id} (للمالك أو المدير المباشر)
3. PUT /rights/{id}/approve (للمدير المالي فقط)

❌ ما لا يجب أن يصل إليه هذا السياق أبداً:
• كشوف الحسابات البنكية
• مفاتيح جلسات المستخدمين
• بيانات التكامل الخارجية
2. سياق التحقق المحمي (Verification Protected Context)
yaml
المسؤولية الأمنية:
• التحقق من صحة إثباتات الدفع
• حماية بيانات التحقق المالية
• اكتشاف المحاولات الاحتيالية

حدود الثقة:
• يعامل جميع البيانات الخارجية كغير موثوقة
• يتحقق من مصداقية كل مصدر بيانات

طريقة المصادقة:
• API Keys للخدمات الداخلية
• HMAC Verification للمصادر الخارجية
• خدمة التوقيع المشفرة لكل نتيجة تحقق

نموذج التخويل:
• ABAC فقط:
  - يمكنه الوصول لإثباتات دفع موظفيه فقط
  - يحتاج موافقة مسبقة للوصول لكشوف بنكية
  - يتحقق من صلاحية الوصول لكل ملف

الأسرار المملوكة:
• مفاتيح وصول لـ APIs خارجية
• مفاتيح تحقق لتوقيعات Webhooks
• مفاتيح تشفير لنتائج التحقق

نقاط الدخول المسموحة فقط:
1. POST /verify/payment (من خدمة الإشعارات فقط)
2. GET /verify/{id}/result (للموظف المعني أو مديره)
3. POST /verify/webhook/{gateway} (من منصات الدفع فقط)

❌ ما لا يجب أن يصل إليه هذا السياق أبداً:
• قواعد العمولات المالية
• معلومات تسجيل دخول المستخدمين
• بيانات الشركات المنافسة
3. سياق الهوية المحمي (Identity Protected Context)
yaml
المسؤولية الأمنية:
• إدارة هويات المستخدمين بشكل آمن
• حماية مفاتيح الجلسات
• التحكم في سلسلة الصلاحيات

حدود الثقة:
• الثقة الصفرية حتى بين مستخدمين في نفس الشركة
• كل عملية مصادقة مستقلة

طريقة المصادقة:
• Multi-factor عند الطلب
• Session tokens مشفرة
• Device fingerprinting

نموذج التخويل:
• RBAC مع Herarchical Roles:
  - Owner → Manager → Employee
  - System Admin → Service Account
  - Auditor → Read-only Access

الأسرار المملوكة:
• Private keys لتوقيع JWTs
• Encryption keys لبيانات المستخدمين
• Secrets لخدمات المصادقة

نقاط الدخول المسموحة فقط:
1. POST /auth/login (من الواجهات الأمامية فقط)
2. POST /auth/validate (من الـ API Gateway فقط)
3. GET /auth/permissions (للخدمات الداخلية فقط)

❌ ما لا يجب أن يصل إليه هذا السياق أبداً:
• بيانات العمولات المالية
• محتوى الملفات والمستندات
• قواعد العمل التجارية
4. سياق التسوية المحمي (Settlement Protected Context)
yaml
المسؤولية الأمنية:
• حماية سرية النزاعات
• ضمان حيادية التحكيم
• تأمين بيانات السمعة

حدود الثقة:
• ثقة محسوبة بناءً على الأدلة
• تحقق من كل مصدر أدلة

طريقة المصادقة:
• Proof-of-Ownership للأدلة
• Digital signatures للقرارات
• Timestamp verification

نموذج التخويل:
• Context-aware ABAC:
  - الوصول للنزاعات التي أنشأها أو كلف بها
  - صلاحيات محددة بناءً على حالة النزاع
  - تسجيل الوصول لجميع الإجراءات

الأسرار المملوكة:
• مفاتيح توقيع قرارات التحكيم
• مفاتيح تشفير أدلة النزاعات
• مفاتيح حساب درجات السمعة

نقاط الدخول المسموحة فقط:
1. POST /settlement/dispute (للموظف المعني فقط)
2. GET /settlement/{id} (لأطراف النزاع فقط)
3. POST /settlement/{id}/resolve (للمحكم المكلف فقط)

❌ ما لا يجب أن يصل إليه هذا السياق أبداً:
• حسابات الدفع المباشرة
• معلومات اتصال العملاء
• أسرار تكامل الأنظمة الخارجية
5. سياق التدقيق المحمي (Audit Protected Context)
yaml
المسؤولية الأمنية:
• ضمان عدم إنكار الإجراءات
• حماية سجلات التدقيق من التعديل
• توفير إثباتات قانونية

حدود الثقة:
• لا يثق في أي بيانات تأتيه
• يتحقق من صحة كل حدث
• يوقع رقمياً كل تسجيل

طريقة المصادقة:
• Cryptographic proof للأحداث
• Chain of custody للأدلة
• Immutable storage

نموذج التخويل:
• Read-only للجميع (بعد الحدث)
• Write-once للخدمات المصدرة
• Verify-only للمراجعين

الأسرار المملوكة:
• Private keys للتوقيع الرقمي
• Hashing keys للسلاسل الزمنية
• Encryption keys للأرشفة

نقاط الدخول المسموحة فقط:
1. POST /audit/event (من الخدمات الداخلية فقط)
2. GET /audit/trail/{id} (للمراجعين المعتمدين فقط)
3. POST /audit/prove (لخدمة التوقيع المشفرة فقط)

❌ ما لا يجب أن يصل إليه هذا السياق أبداً:
• بيانات المستخدمين الحية
• مفاتيح تشغيل النظام
• اتصالات الشبكة المباشرة
🔐 PHASE 2 — نموذج الهوية والوصول
نظام الهوية المركزي المنفصل:
مزود الهوية (Identity Provider):
yaml
الهيكل:
• Identity Service (IdP) مستقل
• Tenant-aware Identity Store
• Role & Permission Registry
• Session Management Service

الهويات:
1. User Identity:
   • userId + tenantId + deviceId
   • Multi-factor authentication
   • Session lifetime محددة

2. Service Identity:
   • serviceId + purpose + scope
   • API Keys مع rotation
   • Mutual TLS authentication

3. System Identity:
   • systemId + component + trustLevel
   • Hardware-backed keys
   • Automated certificate management
التسلسل الهرمي للأدوار حسب المستأجر:
text
مالك الشركة (Tenant Owner)
    ├── المدير المالي (Finance Manager)
    ├── مدير الموارد البشرية (HR Manager)
    ├── مدير التشغيل (Operations Manager)
    │       ├── مدير القسم (Department Manager)
    │       │       ├── مشرف (Supervisor)
    │       │       └── موظف (Employee)
    │       └── موظف بدوام جزئي (Part-Time)
    └── المحلل (Analyst)
نموذج الصلاحيات (الحبيبية على مستوى الإجراء):
yaml
صلاحيات مالية:
• commission:calculate (للموظف: نعم، للمدير: نعم)
• commission:approve (للموظف: لا، للمدير: نعم، لحد 5000)
• commission:override (للموظف: لا، للمدير المالي: نعم)

صلاحيات المهام:
• task:create (للمدير: نعم، للموظف: لا)
• task:complete (للموظف: نعم، للمشرف: نعم)
• task:verify (للمشرف: نعم، للموظف: لا)

صلاحيات النظام:
• system:monitor (لـ System Admin فقط)
• audit:read (للمراجع المعتمد فقط)
• config:modify (للمالك فقط)
تدفق الطلب المصادق عليه:
text
1. المستخدم ← يرسل طلباً ← Frontend
2. Frontend ← يضيف JWT ← Local Storage
3. الطلب ← يصل لـ API Gateway
4. API Gateway ← يرسل JWT ← Identity Service
5. Identity Service ← يتحقق:
   • Signature validation
   • Token expiration
   • Tenant context
   • Device verification
6. Identity Service ← يرجع:
   • isValid: true/false
   • userId, tenantId, roles[]
   • permissions: {action: resource}
   • sessionInfo
7. API Gateway ← يمرر الطلب ← الخدمة المستهدفة
8. الخدمة ← تتحقق محلياً:
   • هل userId موجود في tenantId؟
   • هل role مصرح بهذا الإجراء؟
   • هل permission موجود؟
   • هل within business hours؟
9. الخدمة ← تنفذ ← ترجع النتيجة
منع تصعيد الصلاحيات:
ضوابط التصعيد:
yaml
1. فصل الصلاحيات:
   • لا يمكن أن يكون الشخص مديراً ومحاسباً
   • لا يمكن الموافقة على عمولاتك الخاصة

2. حدود مالية:
   • المدير: حتى 5000 ريال
   • المدير المالي: حتى 50000 ريال
   • المالك: غير محدود

3. توقيع مزدوج:
   • المعاملات الكبيرة تحتاج موافقتين
   • كل موافقة من جهاز مختلف

4. تسجيل التصعيد:
   • كل طلب تصعيد يسجل
   • يحتاج موافقة من مستوي أعلى
   • يرسل إشعاراً للمالك
آلية اكتشاف التصعيد غير المصرح:
text
1. نظام المراقبة يكتشف:
   • مستخدم يحاول الوصول لصلاحيات أعلى من دوره
   • طلبات متكررة لنفس الصلاحية المرفوضة
   • أوقات عمل غير معتادة

2. الرد التلقائي:
   • تجميد الجلسة المؤقت
   • إرسال إشعار للمسؤول
   • تسجيل في سجلات التدقيق

3. المراجعة البشرية:
   • مراجعة السجل الكامل
   • اتخاذ قرار بالتجميد أو السماح
   • تحديث سياسات الوصول إذا لزم
🛡️ PHASE 3 — التخويل على مستوى المجال
تجميع الحقوق (Rights Aggregate):
من يمكنه:
yaml
إنشاء (Create):
• System فقط (عند اكتشاف إنجاز)
• يحتاج: commission:calculate permission
• يتحقق من: employee.belongsTo(tenant)

تعديل (Modify):
• لا أحد (Immutable after calculation)
• الاستثناء: Manager مع commission:override
• يحتاج: موافقة مزدوجة للمبالغ الكبيرة

الموافقة (Approve):
• Manager مع commission:approve
• Finance Manager للجميع
• يتحقق من: approver ≠ employee

المشاهدة (View):
• Employee (لنفسه فقط)
• Manager (لفريقه فقط)
• Owner (للكل في شركته)
الثوابت المحمية بالتخويل:
yaml
1. ثابت الملكية:
   • Right.employee.tenantId == User.tenantId
   • لا يمكن عرض حقوق من شركة أخرى

2. ثابت التوقيت:
   • لا يمكن تعديل الحقوق بعد 24 ساعة
   • لا يمكن الموافقة بعد 7 أيام

3. ثابت المبلغ:
   • لا يمكن الموافقة على مبلغ > الحد المسموح
   • لا يمكن لمدير الموافقة على عمولاته

4. ثابت الحالة:
   • Right.status == 'calculated' قبل الموافقة
   • Right.status == 'approved' قبل الدفع
التحولات المحظورة بين الحالات:
text
❌ calculated → calculated (لا إعادة حساب)
❌ approved → pending (لا تراجع بعد الموافقة)
❌ paid → approved (لا تعديل بعد الدفع)
❌ disputed → paid (لا دفع أثناء النزاع)
تجميع التحقق (Verification Aggregate):
من يمكنه:
yaml
إنشاء (Create):
• System فقط (عند إخطار بالدفع)
• Employee (عند رفع إثبات دفع)
• يحتاج تحقق من ملكية الإثبات

تعديل (Modify):
• لا أحد (Immutable after creation)
• يمكن إضافة أدلة إضافية فقط

الموافقة (Approve):
• Verification Service فقط
• بناءً على قواعد التحقق الآلي
• يمكن رفع للتحقق البشري

المشاهدة (View):
• Employee (لإثباتاته فقط)
• Manager (لإثباتات فريقه)
• Auditor (لجميع الإثباتات)
القواعد الأمنية داخل المجال:
yaml
قاعدة التوقيع الرقمي:
• كل إثبات يجب أن يكون موقّعاً
• التوقيع من مصدر موثوق
• صلاحية التوقيع محددة

قاعدة السلسلة الزمنية:
• توقيت الرفع مسجل
• توقيت التحقق مسجل
• التسلسل الزمني محفوظ

قاعدة الإسناد:
• كل إثبات مرتبط بحق معين
• لا يمكن إسناد إثبات لحق منتهي
• التحقق من تطابق المبالغ
تجميع النزاع (Dispute Aggregate):
من يمكنه:
yaml
إنشاء (Create):
• Employee فقط (لحقوقه)
• يحتاج: حق في حالة 'paid' أو 'rejected'
• يتحقق من: لم يفتح نزاعاً سابقاً على نفس الحق

تعديل (Modify):
• Dispute Parties فقط (إضافة أدلة)
• Arbitrator (تحديث حالة)
• System (تطبيق القرار)

الموافقة (Approve):
• Arbitrator المعين فقط
• يحتاج: مراجعة كافة الأدلة
• يحتاج: توقيع رقمي للقرار

المشاهدة (View):
• Dispute Parties فقط
• Arbitrator المعين
• Auditor المعتمد
الثوابت الأمنية:
yaml
1. ثابت الحيادية:
   • Arbitrator لا ينتمي لنفس قسم الأطراف
   • Arbitrator ليس له مصلحة مباشرة

2. ثابت السرية:
   • أدلة النزاع مشفرة
   • الوصول مقصور على الأطراف
   • المحفوظات مشفرة

3. ثابت الإلزام:
   • القرار النهائي ملزم
   • التطبيق آلي عند القرار
   • لا يمكن تجاهل القرار
💰 PHASE 4 — أمن العمليات المالية والعمولات
حدود الاتساق القوية للنظام المالي:
الحدود:
yaml
1. حدود حساب العمولة:
   • كل حساب عمولة داخل transaction واحدة
   • لا قراءات متزامنة أثناء الحساب
   • Commit فقط بعد التحقق الكامل

2. حدود الموافقة:
   • الموافقة = قفل الحق + تسجيل الموافقة
   • لا يمكن تعديل بعد الموافقة
   • كل تغيير يحتاج نزاعاً رسمياً

3. حدود الدفع:
   • التحقق من الدفع = تحديث حالة الحق
   • لا يمكن تحديث حالة إذا كانت 'paid'
   • كل تحديث حالة مسجل في ledger
عمليات غير متكررة (Idempotent Operations):
yaml
مفتاح عدم التكرار (Idempotency Key):
• مطلوب لكل عملية مالية
• توليد: userId + timestamp + operationHash
• تخزين: Redis مع TTL 24 ساعة
• التحقق: قبل أي عملية مالية

العمليات المدعومة:

1. حالة الحقوق (Right Status):
   • pending → approved → paid

   • كل دفع له معرف فريد
   • التحقق من التكرار قبل التسجيل

الطبقات:
1. التوقيع الرقمي (Digital Signature):
   • توقيع كل حدث بخدمة التوقيع
   • التحقق قبل المعالجة
   • رفض الأحداث غير الموقعة

2. سلسلة الكتل الداخلية (Internal Blockchain):
   • كل حدث له hash
   • hash السابق في الحدث التالي
   • سلسلة غير قابلة للكسر

3. التخزين الكتابي الواحد (Write-Once Storage):
   • Append-only event store
   • Immutable after write
   • Cryptographic proof of write
ملكية الحدث (Event Ownership):
yaml
قواعد الملكية:
1. المصدر (Source Ownership):
   • فقط الخدمة المالكة يمكنها نشر أحداث
   • التحقق من هوية الخدمة الناشرة
   • رفض الأحداث من مصادر غير مصرحة

2. النطاق (Scope Ownership):
   • الأحداث تحتوي tenant_id
   • الأحداث تحتوي aggregate_id
   • لا أحداث عامة بدون تحديد نطاق

3. دورة الحياة (Lifecycle Ownership):
   • الخدمة المالكة تتحكم في retention
   • لا يمكن حذف الأحداث
   • يمكن أرشفة بعد فترة

yaml
1. المالك (Owner):
   • سجلات شركته فقط
   • لا يمكن تعديل أو حذف
   • يمكن تصدير بتوقيع رقمي

2. المراجع (Auditor):
   • وصول قراءة فقط
   • لجميع السجلات في نطاق التحقيق

3. النظام (System):
   • وصول للكشف عن الشذوذ
   • قراءة مجمعة فقط
   • لا وصول للبيانات التفصيلية

4. السلطات (Authorities):
   • بأمر قضائي فقط
   • وصول محصور بموجب الأمر
   • تسجيل كل وصول

text

1. التوقيع الرقمي:

   • توقيع جماعي للسجلات المجمعة
   • التحقق الدوري للتواقيع

2. سلسلة الكتل:
   • hash كل دفعة سجلات
   • hash السابق في الدفعة التالية
   • تخزين hashes في blockchain منفصل

3. النسخ المتعددة:
   • نسخة رئيسية (كتابة)
   • نسخة قراءة فقط (نسخ متماثل)

4. المراقبة المستمرة:
   • مراقبة integrity hashes
   • اكتشاف التغيرات غير المصرحة
   • إشعارات فورية للشذوذ
