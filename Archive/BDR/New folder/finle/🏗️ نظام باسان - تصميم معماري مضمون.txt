🔐 PHASE 1 — النطاقات المحددة الآمنة (Secure Bounded Contexts)
2.1 نطاق الهوية والوصول (Identity & Access Context)
yaml
المسؤولية الأمنية:
• إدارة الهوية والتواقيع
• تطبيق سياسات الوصول
• تسجيل أحداث المصادقة

حدود الثقة:
• لا يثق به أي نطاق آخر تلقائياً
• يجب أن يتحقق كل طلب من الهوية
• الإثباتات المشفرة لكل عملية

المصادقة:
• JWT مع إثبات التملك (Proof of Possession)
• مفاتيح غير متناظرة لكل خدمة
• مدة صلاحية قصيرة (دقائق)

التخويل:
• نموذج ABAC (Attribute-Based Access Control)
• سياسات مبنية على السياق
• تقييم لكل طلب بشكل منفصل

الأسرار المملوكة:
• مفاتيح توقيع JWT
• مفاتيح تشفير للمستأجرين
• كلمات مرور مشفرة

نقاط الدخول المسموحة فقط:
1. POST /authenticate (المصادقة)
2. POST /authorize (التحقق من الصلاحية)
3. POST /audit/log (تسجيل الأحداث)

❌ ما يجب أن لا يصل إليه هذا النطاق أبداً:
• البيانات المالية (العمولات، المدفوعات)
• بيانات PII للموظفين
• مستندات وأدلة الإنجازات

🆔 PHASE 2 — نموذج الهوية والوصول المركزي المنفصل
3.1 مقدم الهوية (Identity Provider - IdP)
الهوية المعرفة بالمستأجر:
yaml
الهيكل:
User Identity = Tenant ID + User ID + Role Hierarchy
كل هوية:
• tenant_id: UUID للشركة
• user_id: UUID للمستخدم داخل الشركة
• role_path: ["owner", "sales_manager", "team_lead"]
• permissions: {resource:action:conditions}
تدفق المصادقة:
text
1. Client Request → API Gateway
   Headers: {Authorization: Bearer <token>}
   
2. API Gateway → Identity Context
   Request: Validate(token, tenant_id, requested_action)
   
3. Identity Context Validation:
   • Verify JWT Signature
   • Check Token Expiry
   • Validate Tenant Ownership
   • Evaluate Permission Policy
   
4. Response:
   • Valid: {user_id, role_path, permissions, tenant_context}
   • Invalid: 401 Unauthorized
   • Insufficient: 403 Forbidden
نموذج الصلاحيات:
yaml
مستوى الحبوب: Action-level
البنية:
Permission = Resource + Action + Conditions

أمثلة:
1. Owner:
   • companies:*
   • employees:*
   • commissions:*
   • disputes:*

2. Department Manager:
   • employees:read (own_department)
   • commissions:approve (amount < 5000)
   • tasks:create (own_department)
   • reports:read (own_department)

3. Employee:
   • employees:read:self
   • commissions:read:self
   • tasks:read:assigned
   • evidence:upload:self

4. HR Manager:
   • employees:*
   • contracts:*
   • disputes:mediate
   • training:manage
منع تصعيد الصلاحيات:
yaml
القواعد:
1. No Permission Inheritance:
   • كل دور له صلاحيات صريحة
   • لا توريث تلقائي من الأدوار الأعلى
   
2. Action Validation:
   • كل طلب يتم التحقق من الصلاحية
   • حتى لو كان من نفس المستخدم
   
3. Context Boundary:
   • صلاحية في نطاق ≠ صلاحية في نطاق آخر
   • التحقق من حدود النطاق مع كل طلب
   
4. Audit Every Override:
   • أي تجاوز للصلاحيات مسجل
   • يتطلب موافقة من مستوى أعلى
   • مراجعة أسبوعية للتجاوزات
3.2 إنفاذ التخويل:
في مستوى النطاق (Domain Level):
typescript
class CommissionAggregate {
    async calculateCommission(saleData, userContext) {
        // التحقق من الصلاحية داخل منطق النطاق
        if (!this.canCalculate(userContext)) {
            throw new AuthorizationError("Not authorized to calculate commissions");
        }
        
        // التحقق من السياق
        if (userContext.tenant_id !== this.company.tenant_id) {
            throw new TenantIsolationError("Cross-tenant access denied");
        }
        
        // تطبيق قواعد الأعمال
        return this.calculate(saleData);
    }
    
    canCalculate(userContext) {
        return userContext.hasPermission('commissions:calculate') &&
               userContext.isDepartmentManager(this.department_id);
    }
}
في مستوى الخدمة (Service Level):
yaml
المخطط:
1. كل خدمة تستقبل UserContext
2. تتحقق من:
   • صحة التوكن
   • مطابقة tenant_id
   • وجود الصلاحية المطلوبة
   • شروط الصلاحية (conditions)
3. ترفض أي طلب بدون السياق الكامل
🛡️ PHASE 3 — التخويل على مستوى النطاق
4.1 مجموعة الشركة (Company Aggregate)
من يمكنه:
yaml
إنشاء (Create):
• System (للشركات الجديدة)
• Owner (لإضافة فروع)

تعديل (Modify):
• Owner فقط
• مع تسجيل سبب التعديل

الموافقة (Approve):
• مخصص للنظام (لا موافقة بشرية)

عرض (View):
• Owner: عرض كامل
• Managers: عرض محدود (قسمهم)
• Employees: عرض أساسي فقط
الدوال الثابتة المحمية بالتخويل:
yaml
1. تغيير الهيكل التنظيمي:
   • يجب أن يكون المستخدم Owner
   • يجب تسجيل سبب التغيير
   • يجب إخطار جميع المتأثرين
   
2. تعديل قواعد العمولات:
   • يحتاج موافقة Owner + Finance Manager
   • لا ينطبق بأثر رجعي إلا بموافقة
   • نسخ احتياطي من القواعد القديمة
   
3. إضافة/حذف قسم:
   • Owner فقط
   • لا حذف إذا كان فيه موظفين
   • نقل جميع الموظفين أولاً
التحولات المحظورة:
yaml
1. من "نشط" إلى "محذوف":
   • ممنوع مباشرة
   • يجب المرور بـ "معلق" أولاً
   • فترة احتفاظ 30 يوم
   
2. تغيير tenant_id:
   • ممنوع نهائياً
   • يلغي جميع بيانات المستأجر
   
3. نقل ملكية الشركة:
   • عملية خاصة (Transfer Aggregate)
   • توقيعات متعددة
   • تدقيق كامل

من يمكنه:
yaml

yaml

   • نسخ من العقد القديم
   
2. تحديث الحساب البنكي:
   • الموظف نفسه فقط
   • تحقق من الملكية (OTP)
   • تأخير 24 ساعة للتطبيق
   
3. إضافة مهارة/شهادة:
   • الموظف (للإضافة)
   • HR Manager (للتحقق)

yaml

• الموظف نفسه

yaml

   • System فقط

2. دفع العمولة:
   • Finance Manager فقط
   • موافقة مزدوجة للمبالغ الكبيرة
   • إغلاق السجل بعد الدفع

   • Finance Manager + Owner

yaml

   • ممنوع
   • التعديلات قبل الدفع فقط
   
3. دفع عمولة بدون حساب بنكي:
   • ممنوع
   • يجب التحقق من الحساب أولاً
💰 PHASE 4 — الأمان المالي ومحرك العمولات
5.1 حدود الاتساق القوية:
حدود المعاملات المالية:
yaml
كل شركة = حدود اتصاق منفصلة
الداخل:
• حسابات الموظفين
• سجل العمولات
• سجل المدفوعات

ضمانات:
• Atomic per company
• Eventual consistency between companies
• Strong consistency within company
عمليات غير قابلة للتكرار (Idempotent):
yaml
لكل عملية مالية:
1. Idempotency Key:
   • UUID فريد لكل طلب
   • مخزن في Redis مع TTL
   • مرفوض إذا وجد مسبقاً
   
2. Request Hashing:
   • Hash لبيانات الطلب
   • مخزن مع Idempotency Key
   • مطابقة Hash للطلبات المتكررة
   
3. Result Caching:
   • نتيجة العملية مخزنة
   • إرجاع نفس النتيجة للطلبات المتكررة
   • TTL حسب نوع العملية
5.2 منع الإنفاق المزدوج (Double-spend Prevention):
