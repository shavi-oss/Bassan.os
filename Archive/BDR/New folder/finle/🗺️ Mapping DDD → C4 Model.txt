🗺️ Mapping DDD → C4 Model لنظام "باسان"
🎯 الفلسفة الربطية
القاعدة الأساسية:
text
DDD (Domain-Driven Design) ← يحدد "ماذا"
C4 Model ← يحدد "كيف"

DDD: التركيز على النطاق التجاري
C4: التركيز على الهيكل التقني
📊 الجدول الربطي الكامل
DDD Concept	C4 Counterpart	مثال في نظام "باسان"	ملاحظات الربط
النطاق التجاري (Business Domain)	System Context	• نطاق الحقوق
• نطاق الإنجازات
• نطاق التحقق	DDD يحدد النطاقات، C4 يحدد حدود النظام
النطاق المحدد (Bounded Context)	Container	• خدمة الحقوق (Rights Service)
• خدمة الإنجازات (Achievement Service)	كل Bounded Context ≈ حاوية مستقلة
الوحدة المجمعة (Aggregate)	Component	• حاسب الحقوق (Rights Calculator)
• محقق المدفوعات (Payment Investigator)	Aggregate ≈ مجموعة من المكونات المنطقية
الكيان (Entity)	Database Table/Entity	• Employee (جدول الموظفين)
• Commission (جدول العمولات)	Entity ≈ نموذج بيانات في قاعدة البيانات
الكائن القيمة (Value Object)	Data Transfer Object	• CommissionRule (قاعدة العمولة)
• PaymentVerification (نتيجة التحقق)	VO ≈ كائن بيانات يمر بين المكونات
المستودع (Repository)	Data Access Component	• Rights Repository
• Achievement Repository	Repository ≈ مكون الوصول للبيانات
خدمة النطاق (Domain Service)	Business Logic Component	• Rule Engine (محرك القواعد)
• Verification Engine (محرك التحقق)	Domain Service ≈ مكون منطق الأعمال
حدث النطاق (Domain Event)	Message/Event	• RightsCalculated (حقوق محسوبة)
• PaymentVerified (دفع تم التحقق منه)	Domain Event ≈ رسالة في Event Bus
وحدة المجال (Module)	Package/Namespace	• rights.calculator
• verification.payment	Module ≈ هيكل المجلدات/التسمية
سياق الخريطة (Context Map)	Container Diagram	• تدفق البيانات بين الخدمات
• اعتماديات بين الحاويات	Context Map ≈ رسم تخطيطي للحاويات
لغة منتشرة (Ubiquitous Language)	Glossary/Dictionary	• موظف (Employee)
• عمولة (Commission)
• مهمة (Task)	لغة مشتركة في الوثائق والكود
الطبقة المضادة للفساد (Anti-Corruption Layer)	Adapter/Integration Service	• Shopify Adapter
• Payment Gateway Adapter	ACL ≈ خدمة تكامل مع أنظمة خارجية

1. نطاق الحقوق (Rights Domain)
DDD Structure:
yaml
Aggregates:
  1. CommissionAggregate:
     • Entities: Commission, Employee
     • Value Objects: CommissionRule, CalculationResult
     • Domain Services: RightsCalculator
     • Repositories: CommissionRepository
     • Domain Events: RightsCalculated, CommissionApproved

  2. RuleAggregate:
     • Entities: CommissionRule
     • Value Objects: RuleCondition, RuleAction
     • Domain Services: RuleEngine
     • Repositories: RuleRepository
     • Domain Events: RuleCreated, RuleModified
C4 Mapping:
yaml
Container: Rights Service
Components:
  1. Rights Calculator (Domain Service)
     • Responsibility: حساب الحقوق
     • Dependencies: Rule Repository, Commission Repository
     
  2. Rule Engine (Domain Service)
     • Responsibility: تطبيق القواعد
     • Dependencies: Rule Repository, Historical Context Engine
     
  3. Rights Repository (Repository)
     • Responsibility: وصول بيانات الحقوق
     • Storage: PostgreSQL - Rights Database
     
  4. Rule Repository (Repository)
     • Responsibility: وصول بيانات القواعد
     • Storage: PostgreSQL - Rules Database

// في نطاق التحقق
class PaymentVerificationAggregate {
  // يستمع لحدث من نطاق الحقوق
  @Subscribe(RightsCalculatedEvent)
  async handleRightsCalculated(event: RightsCalculatedEvent) {
    // تحقق من الدفع المقابل لهذا الحق
    await this.verifyPayment(event.rightId, event.amount);
  }
}
النمط 2: استدعاء مباشر عبر APIs (إذا كان ضرورياً)
typescript
// في نطاق التسوية
class ReputationAnalyzer {
  constructor(
    private rightsService: RightsServiceClient, // RPC Client
    private verificationService: VerificationServiceClient
  ) {}
  
  async analyzeCompanyReputation(companyId: string) {
    // استدعاء مباشر (نادر، يفضل الأحداث)
    const paymentHistory = await this.verificationService
      .getPaymentHistory(companyId);
      
    const rightsCompliance = await this.rightsService
      .getComplianceRate(companyId);
      
    return this.calculateReputation(paymentHistory, rightsCompliance);
  }
}

🚨 قواعد الربط والحدود
قاعدة 1: حدود النطاق = حدود الحاوية
text
إذا كان هناك Bounded Context جديد في DDD:
• يجب أن يكون Container جديد في C4
• له قاعدة بيانات منفصلة (إن أمكن)
• اتصالات محددة عبر APIs/Events
قاعدة 2: Aggregate ≈ مجموعة مكونات
text
Aggregate في DDD يتكون من:
• 1+ Entities
• 0+ Value Objects
• 0+ Domain Services
• 1 Repository

وهذا يترجم في C4 إلى:
• 1+ Components داخل Container
• قد يحتاج قاعدة بيانات منفصلة
• ينشر/يستمع لأحداث محددة
قاعدة 3: الابتعاد عن الاقتران المباشر
text
❌ سيء: Rights Service يتصل مباشرة بـ Verification Database
❌ سيء: Achievement Service يستدعي Settlement Service مباشرة

✅ جيد: Rights Service ينشر RightsCalculatedEvent
✅ جيد: Verification Service يستمع للحدث ويستجيب
✅ جيد: البيانات المشتركة في Shared Database
قاعدة 4: التكاملات الخارجية كـ Anti-Corruption Layer
text
أنظمة خارجية (Shopify, Telegram, etc.):
• في DDD: تعامل كنطاقات خارجية
• في C4: Integration Service + Adapters
• الفصل: لا تسمح للتأثيرات الخارجية بفساد النطاقات الداخلية
📈 تحليل الربط لسيناريوهات معقدة
سيناريو: نزاع على عمولة
DDD Analysis:
yaml
النطاقات المشاركة:
1. Rights Domain:
   • Aggregate: CommissionAggregate
   • Event: CommissionDisputed
   
2. Achievement Domain:
   • Aggregate: EvidenceAggregate
   • Event: EvidenceRequested
   
3. Verification Domain:
   • Aggregate: PaymentVerificationAggregate
   • Event: PaymentReexamined
   
4. Settlement Domain:
   • Aggregate: DisputeAggregate
   • Event: DisputeResolved
C4 Implementation:
yaml
التفاعل بين الحاويات:
1. Rights Service:
   • ينشر: CommissionDisputedEvent
   
2. Achievement Service (يستمع للحدث):
   • يجمع الأدلة ذات الصلة
   • ينشر: EvidenceCollectedEvent
   
3. Verification Service (يستمع للأحداث):
   • يعيد فحص التحقق
   • ينشر: VerificationUpdatedEvent
   
4. Settlement Service (يستمع لكل الأحداث):
   • يجمع كل المعلومات
   • يحلل النزاع
   • يتخذ قرار التحكيم
   • ينشر: DisputeResolvedEvent
   
5. جميع الخدمات (تستمع للقرار):
   • تحديث البيانات الداخلية
   • تعديل السمعة إذا لزم
الكود المقابل:
typescript
// في Settlement Service
class DisputeResolver {
  @Subscribe(CommissionDisputedEvent)
  @Subscribe(EvidenceCollectedEvent)
  @Subscribe(VerificationUpdatedEvent)
  async resolveDispute(events: DomainEvent[]) {
    const dispute = this.createDisputeCase(events);
    const decision = await this.arbitrate(dispute);
    
    await this.publish(new DisputeResolvedEvent(decision));
    
    // تحديث السمعة في نفس النطاق
    await this.updateReputation(
      dispute.companyId, 
      dispute.employeeId, 
      decision
    );
  }
}
🎯 أفضل الممارسات في الربط
1. الحفاظ على استقلالية النطاقات
yaml
ممارسة صحيحة:
• كل نطاق له قاعدة بيانات خاصة (إن أمكن)
• الاتصال فقط عبر Events/APIs محددة
• لا مشاركة للنماذج الداخلية

ممارسة خاطئة:
• استيراد Entities من نطاق آخر
• الوصول المباشر لقاعدة بيانات نطاق آخر
• الاقتران المباشر بين Domain Services
2. تصميم الأحداث بعناية
yaml
أحداث جيدة:
• CommissionCalculated (حقوق محسوبة)
• PaymentVerified (دفع تم التحقق)
• TaskCompleted (مهمة مكتملة)

أحداث سيئة:
• EmployeeDataChanged (تغيير بيانات موظف - عام جداً)
• SystemUpdated (تحديث نظام - غير محدد)
• EverythingHappened (كل شيء حدث - غير مفيد)
3. إدارة البيانات المشتركة
yaml
البيانات التي يمكن مشاركتها:
• Employee Basic Info (اسم، بريد، هاتف)
• Company Basic Info (اسم، صناعة)
• Product Catalog (منتجات، أسعار)

البيانات التي لا تشارك:
• Commission Calculations (حسابات خاصة بالنطاق)
• Payment Details (تفاصيل مالية حساسة)
• Dispute Discussions (مناقشات نزاع خاصة)
4. تصميم الـ APIs بين النطاقات
yaml
REST APIs (للحالات النادرة):
• GET /api/rights/summary/{employeeId}
• POST /api/verification/verify-payment
• PUT /api/settlement/reputation/{companyId}

gRPC (للأداء العالي):
• rights.GetCommissionSummary
• verification.VerifyPayment
• settlement.CalculateReputation

Events (الأفضل غالباً):
• rights.calculated
• payment.verified
• dispute.resolved

✅ الخلاصة: DDD + C4 = تصميم متكامل
مزايا الربط:
yaml
1. وضوح الهيكل:
   • DDD: يحدد "لماذا" و"ماذا"
   • C4: يحدد "كيف" و"أين"

2. قابلية الصيانة:
   • تغييرات في النطاق ← تغييرات في الحاوية فقط
   • حدود واضحة ← أخطاء محدودة الانتشار

3. قابلية التوسع:
   • نطاق جديد ← حاوية جديدة
   • نمو في النطاق ← توسع في الحاوية

4. الاتساق:
   • نفس اللغة في جميع المستويات
   • نفس المبادئ في التصميم والتنفيذ
