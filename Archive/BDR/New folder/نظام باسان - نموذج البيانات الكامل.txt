تعريف الكيانات (Entities)
1. companies (الشركات)
الغرض: تخزين بيانات الشركات المشتركة

المسؤولية: وحدة إدارة الشركات

دورة الحياة: إنشاء → تفعيل → تحديث → إلغاء (نادر)

حساسية البيانات: متوسطة (بيانات أعمال)

2. employees (الموظفين)
الغرض: بيانات الموظفين الشخصية والتعاقدية

المسؤولية: وحدة إدارة الموظفين

دورة الحياة: توظيف → تحديث → ترقية → مغادرة

حساسية البيانات: عالية (PII، بيانات مالية)

3. departments (الأقسام)
الغرض: الهيكل التنظيمي للشركة

المسؤولية: وحدة إدارة الأقسام

دورة الحياة: إنشاء → تعديل → دمج → إلغاء

حساسية البيانات: منخفضة

4. commissions (العمولات)
الغرض: سجلات العمولات المحسوبة والمدفوعة

المسؤولية: محرك العمولات

دورة الحياة: حساب → مراجعة → موافقة → دفع → أرشفة

حساسية البيانات: عالية جداً (بيانات مالية)

5. commission_rules (قواعد العمولات)
الغرض: قواعد حساب العمولات القابلة للتخصيص

المسؤولية: محرك العمولات

دورة الحياة: تعريف → تفعيل → تعديل → تعطيل (لا حذف)

حساسية البيانات: عالية (تؤثر على حسابات مالية)

6. tasks (المهام)
الغرض: إدارة المهام والمشاريع

المسؤولية: نظام إدارة المهام

دورة الحياة: إنشاء → توزيع → تنفيذ → مراجعة → إغلاق

حساسية البيانات: متوسطة

7. sales (المبيعات)
الغرض: سجلات عمليات البيع من مصادر خارجية

المسؤولية: وحدة التكاملات

دورة الحياة: استقبال → معالجة → ربط → أرشفة

حساسية البيانات: عالية (بيانات مالية)

8. notifications (الإشعارات)
الغرض: سجلات الإشعارات المرسلة

المسؤولية: نظام الإشعارات

دورة الحياة: إنشاء → إرسال → تتبع → أرشفة

حساسية البيانات: متوسطة

9. audit_logs (سجلات التدقيق)
الغرض: تتبع جميع التغييرات على البيانات الحساسة

المسؤولية: جميع الوحدات (مركزي)

دورة الحياة: تسجيل → تخزين → مراجعة → أرشفة (طويلة الأمد)

حساسية البيانات: عالية (سجلات أمنية)

10. integrations (التكاملات)
الغرض: إعدادات التكامل مع الأنظمة الخارجية

المسؤولية: وحدة التكاملات

دورة الحياة: إعداد → تفعيل → مراقبة → تعطيل

حساسية البيانات: عالية (مفاتيح API)

11. files (الملفات)
الغرض: تخزين الملفات المرفقة

المسؤولية: وحدة التخزين

دورة الحياة: رفع → تخزين → مشاركة → أرشفة

حساسية البيانات: متفاوتة

تعريف الجداول والحقول
1. جدول companies
text
companies:
  id: VARCHAR(50) [PK] - معرف فريد للشركة (مثل: COMP_xxx)
  name: VARCHAR(255) - اسم الشركة الرسمي
  legal_name: VARCHAR(255) - الاسم القانوني
  tax_id: VARCHAR(50) - الرقم الضريبي (حساس)
  country_code: CHAR(2) - رمز الدولة (SA, EG, AE...)
  currency: CHAR(3) - العملة الأساسية (SAR, EGP...)
  timezone: VARCHAR(50) - المنطقة الزمنية
  plan: VARCHAR(20) - خطة الاشتراك (free, business, enterprise)
  settings: JSONB - إعدادات مخصصة للشركة
  status: VARCHAR(20) - الحالة (active, suspended, cancelled)
  created_at: TIMESTAMPZ
  updated_at: TIMESTAMPZ
  version: INTEGER - للتفاؤل المتفائل (optimistic locking)
مبررات التصميم:

id مخصص للنظام (ليس auto-increment) لتفادي التخمين

settings كـ JSONB لمرونة الإعدادات المختلفة

version لمنع التحديثات المتعارضة على نفس السجل

2. جدول employees
text
employees:
  id: VARCHAR(50) [PK] - معرف فريد للموظف (مثل: EMP_xxx)
  company_id: VARCHAR(50) [FK → companies.id] - الشركة التابع لها
  user_id: VARCHAR(50) [UNIQUE] - معرف المستخدم في نظام المصادقة
  employee_code: VARCHAR(20) - كود الموظف الداخلي (مثل: SA-001)
  full_name: VARCHAR(255) - الاسم الكامل
  email: VARCHAR(255) [UNIQUE] - البريد الإلكتروني (PII)
  phone: VARCHAR(20) - رقم الهاتف (PII)
  national_id: VARCHAR(50) - الرقم القومي/الهوية (PII مشفر)
  department_id: VARCHAR(50) [FK → departments.id] - القسم
  position: VARCHAR(100) - المسمى الوظيفي
  employment_type: VARCHAR(20) - نوع التوظيف (full_time, part_time, commission_only)
  contract_data: JSONB - بيانات العقد (راتب أساسي، نسبة عمولة...)
  bank_data: JSONB [مشفر] - بيانات البنك للتحويلات
  status: VARCHAR(20) - الحالة (active, on_leave, terminated)
  permissions: JSONB - مصفوفة الصلاحيات
  hire_date: DATE - تاريخ التعيين
  termination_date: DATE - تاريخ المغادرة (إن وجد)
  created_at: TIMESTAMPZ
  updated_at: TIMESTAMPZ
مبررات التصميم:

national_id و bank_data يجب تشفيرها في قاعدة البيانات

contract_data كـ JSONB لاختلاف هياكل العقود

permissions تخزن كمصفوفة JSON لأداء أفضل

user_id منفصل عن id لفصل الهوية عن البيانات

departments:

4. جدول commissions (الأكثر حساسية)
text
commissions:
  id: VARCHAR(50) [PK] - معرف فريد للعمولة (مثل: COM_yyyymm_xxx)
  company_id: VARCHAR(50) [FK → companies.id]
  employee_id: VARCHAR(50) [FK → employees.id]
  sale_id: VARCHAR(100) - معرف عملية البيع (من النظام الخارجي)
  
  -- المبالغ (يجب أن تكون غير قابلة للتعديل بعد التثبيت)
  amount: DECIMAL(15,2) - مبلغ العمولة النهائي
  currency: CHAR(3) - العملة
  original_amount: DECIMAL(15,2) - المبلغ قبل أي تعديلات
  exchange_rate: DECIMAL(10,6) - سعر الصرف إذا اختلفت العملة
  
  -- تفاصيل الحساب (للمراجعة والتدقيق)
  calculation_snapshot: JSONB - لقطة لحظة الحساب (القواعد، النسب...)
  applied_rule_id: VARCHAR(50) [FK → commission_rules.id NULLABLE]
  
  -- سير العمل
  status: VARCHAR(20) - (pending, under_review, approved, rejected, paid)
  approval_flow: JSONB - مسار الموافقات (من وافق ومتى)
  
  -- التواريخ الحرجة
  calculated_at: TIMESTAMPZ - وقت الحساب
  approved_at: TIMESTAMPZ - وقت الموافقة
  paid_at: TIMESTAMPZ - وقت الدفع الفعلي
  
  -- التتبع
  created_at: TIMESTAMPZ
  updated_at: TIMESTAMPZ
  version: INTEGER
  
  -- للمراجعة المستقبلية
  notes: TEXT - ملاحظات على العمولة
  dispute_id: VARCHAR(50) [FK → disputes.id NULLABLE] - إذا كان هناك نزاع
مبررات التصميم:

id يحتوي على التاريخ (yyyymm) للتجزئة السهلة

calculation_snapshot يحفظ حالة الحساب وقتها (لا يعاد حسابها)

amount و original_amount لمنع التلاعب

version لمنع التحديثات المتعارضة على العمولات

العلاقات والتعددية (Relationships & Cardinality)
العلاقات الأساسية:
company → employees (1:N)

شركة واحدة لديها العديد من الموظفين

employees.company_id يشير إلى companies.id

تأثير الأداء: فهرس مركب على (company_id, status)

company → departments (1:N)

شركة واحدة لديها العديد من الأقسام

departments.company_id يشير إلى companies.id

يمكن أن يكون هرمي: departments.parent_id يشير إلى departments.id

department → employees (1:N)

قسم واحد به العديد من الموظفين

employees.department_id يشير إلى departments.id

employee → commissions (1:N)

موظف واحد له العديد من العمولات

commissions.employee_id يشير إلى employees.id

فهرس مركب على (employee_id, status, created_at)

commission → commission_rules (N:1)

العديد من العمولات تستخدم قاعدة واحدة

commissions.applied_rule_id يشير إلى commission_rules.id

sale → commission (1:1 أو 1:N)

عملية بيع واحدة قد تولد عدة عمولات (لموظفين مختلفين)

commissions.sale_id يشير إلى sales.external_sale_id

employee → tasks (N:M عبر JSONB array)

موظفين كثر يمكن تعيينهم لمهام كثيرة

مخزن في tasks.assigned_to كمصفوفة JSON

بديل: جدول وسيط task_assignments

commission → dispute (1:1)

عمولة واحدة قد يكون لها نزاع واحد

disputes.commission_id يشير إلى commissions.id

العلاقات المعقدة:
text
company (1) → departments (N)
departments (1) → employees (N)  
employees (1) → commissions (N)
commissions (N) → commission_rules (1)
commissions (1) → disputes (0..1)
sales (1) → commissions (1..N)
عزل البيانات متعددة المستأجرين (Multi-Tenancy Isolation)
استراتيجية العزل: Shared Database, Schema per Company ليس، Shared Database مع company_id
بناءً على الملفات: جميع الجداول تحتوي على company_id

آلية التنفيذ:
عزل على مستوى التطبيق:

كل استعلام يجب أن يحتوي WHERE company_id = ?

Middleware يضيف company_id تلقائياً بناءً على JWT

لا يوجد استعلام يمر بدون company_id

عزل على مستوى قاعدة البيانات:

Row-Level Security (RLS) في PostgreSQL:

sql
ALTER TABLE commissions ENABLE ROW LEVEL SECURITY;
CREATE POLICY company_isolation ON commissions
  USING (company_id = current_setting('app.current_company_id'));
عزل على مستوى الفهرس:

جميع الفهارس الأساسية تبدأ بـ company_id:

sql
CREATE INDEX idx_commissions_company_employee 
ON commissions(company_id, employee_id, created_at DESC);
منع تسريب البيانات:

لا توجد JOINs عبر شركات مختلفة

جميع الـ APIs تعيد فقط بيانات شركة المستخدم

company_id في JWT token ويتم التحقق منه في كل طلب

استثناءات العزل:
audit_logs: تحتوي company_id ولكن قد يصل المديرون من شركات مختلفة في المستقبل (مع صلاحيات)

system_logs: للسجلات التشغيلية فقط، بدون بيانات عملاء

سلامة البيانات المالية (Financial Data Safety)
مبادئ التصميم للعمولات:
عدم التعديل (Immutability):

بمجرد أن تصبح العمولة approved أو paid → لا تعديل

أي تصحيح = عمولة جديدة سالبة (Reversal) + عمولة صحيحة

التسجيل المزدوج (Double-Entry Principle):

كل عمولة لها أثر مقابل في audit_logs

calculation_snapshot يحفظ حالة الحساب وقت التنفيذ

عدم التكرار (Idempotency):

sale_id + employee_id + calculation_date يجب أن يكون فريد

منع حساب نفس العمولة مرتين

التسلسل الزمني (Temporal Integrity):

calculated_at ≤ approved_at ≤ paid_at

تحقق عبر قيود CHECK في قاعدة البيانات

قيود سلامة البيانات:
sql
-- مثال لقيود على commissions
ALTER TABLE commissions ADD CONSTRAINT chronological_check 
CHECK (
  (calculated_at IS NOT NULL) AND
  (approved_at IS NULL OR approved_at >= calculated_at) AND
  (paid_at IS NULL OR paid_at >= COALESCE(approved_at, calculated_at))
);

-- منع التكرار
ALTER TABLE commissions ADD CONSTRAINT unique_sale_employee 
UNIQUE (company_id, sale_id, employee_id, calculated_at::DATE);
جداول مساعدة للسلامة المالية:
commission_reversals (للالغاءات والتصحيحات)

payment_batches (لدفعات المجمعة)

financial_periods (لإغلاق الفترات المالية)

مخاطر وفجوات نموذج البيانات
الفجوات الخطيرة:
غياب payment_transactions:

الملفات تذكر commissions.paid_at ولكن لا يوجد تفاصيل الدفع

المخاطر: لا يمكن تتبع التحويلات البنكية، لا مصالحة

الحل: جدول payments منفصل يرتبط بـ commissions

غياب tax_calculations:

لا ذكر للضرائب على العمولات

المخاطر: عدم الامتثال الضريبي

الحل: إضافة tax_amount و tax_rate في commissions

JSONB المفرط:

contract_data, bank_data, calculation_snapshot كلها JSONB

المخاطر: صعوبة الاستعلام، لا قيود على البيانات

الحل: تقسيم إلى جداول منفصلة أو استخدام JSON Schema

غياب budgets و limits:

لا يوجد تتبع للميزانيات الشهرية للعمولات

المخاطر: تجاوز الإنفاق

الحل: جدول commission_budgets مرتبط بـ departments

أخطاء التطبيع (Normalization Issues):
التكرار في commissions:

amount و original_amount يمكن حسابها من calculation_snapshot

المخاطر: تناقض البيانات

الحل: الاحتفاظ بواحدة فقط أو استخدام Views

assigned_to كـ JSONB في tasks:

كسر للقاعدة الأولى للتطبيع

المخاطر: صعوبة تحديث، استعلامات معقدة

الحل: جدول وسيط task_assignments

contract_data في employees:

بيانات العقد يجب أن تكون في جدول employment_contracts

المخاطر: فقدان السجل التاريخي للتغيرات

مشاكل التوسع المستقبلية:
نمو جدول commissions:

عمولة لكل بيع → آلاف السجلات يومياً

الحل: Partitioning بـ company_id و calculated_at

الاستعلامات عبر الشركات:

لا يمكن للمديرين رؤية إحصائيات متعددة الشركات

الحل: read_replicas للتقارير، Data Warehouse منفصل

نسخ commission_rules:
