🎯 النموذج البيئي للنظام (C4 - المستوى 1)
السياق: نظام "باسان"
text
نظام SaaS لإدارة العمولات والموظفين للشركات العربية.
يجمع بين إدارة الموارد البشرية، نظام العمولات الذكي،
الأتمتة الذكية لسير العمل، والتكامل مع أدوات العمل اليومية.
الممثلون الرئيسيون:
مستخدمون بشريون:
👑 صاحب الشركة - يرى الربحية والنمو، يحدد الميزانيات

👔 المدير/مدير القسم - يدير الفريق، يراجع العمولات، يوزع المهام

💼 الموظف بدوام كامل - يتتبع عمولاته، ينجز المهام

🕐 موظف دوام جزئي - يتحكم في وقته، يقبل/يرفض المهام

🚀 موظف بالعمولة فقط - يحصل على فرص، يبني سمعة

🤝 مدير الموارد البشرية - يدير العقود، يتعامل مع النزاعات

🤖 مدير النظام - يراقب الأداء، يحافظ على الاستقرار

📊 المحلل - يحلل البيانات، يقدم توصيات

أنظمة خارجية:
🛒 Shopify Store - مصدر بيانات المبيعات عبر Webhooks

📱 Telegram - قناة إشعارات فورية وأوامر سريعة

📦 نموذج الحاويات (C4 - المستوى 2)
الحاويات الرئيسية:
1. 🌐 واجهة الويب والموبايل (Frontend Applications)
text
• المسؤولية: واجهة المستخدم للتفاعل مع النظام
• التقنية: Next.js (ويب)، React Native (موبايل)
• ملكية البيانات: لا تخزن بيانات، تعرض فقط
• طريقة الاتصال: HTTPS → API Gateway
• حدود الأمان: JWT Authentication، CORS محدود
• المستخدمون: جميع الأدوار البشرية
2. 🤖 بوت Telegram (Telegram Bot)
text
• المسؤولية: واجهة محادثة للموظفين
• التقنية: Telegram Bot API، Node.js
• ملكية البيانات: تخزين مؤقت لسياقات المحادثة
• طريقة الاتصال: Telegram API ←→ Backend APIs
• حدود الأمان: Token-based authentication
• المستخدمون: الموظفون (للإشعارات والأوامر السريعة)
3. 🚪 بوابة API (API Gateway)
text
• المسؤولية: نقطة الدخول الوحيدة لجميع الطلبات
• التقنية: GraphQL + REST، Node.js
• ملكية البيانات: لا تخزن بيانات
• طريقة الاتصال: HTTPS ← Frontend/Bot/External
• حدود الأمان:
  - JWT Validation
  - Rate Limiting
  - Request Logging
  - CORS Management
• البيانات: جميع الطلبات تمر عبره
4. 🧠 خدمة المصادقة والصلاحيات (Auth Service)
text
• المسؤولية: إدارة الهوية والصلاحيات
• التقنية: Node.js + JWT + Redis
• ملكية البيانات: بيانات المستخدمين، الجلسات، الصلاحيات
• طريقة الاتصال: Sync HTTP ← API Gateway
• حدود الأمان:
  - Password Hashing (bcrypt)
  - JWT Token Management
  - Session Management
  - Permission Validation
• قاعدة البيانات: PostgreSQL (users, permissions)
5. 🏢 خدمة الشركات والموظفين (Company & Employee Service)
text
• المسؤولية: إدارة بيانات الشركات والموظفين
• التقنية: Node.js + TypeORM
• ملكية البيانات: companies, employees, departments
• طريقة الاتصال: Sync HTTP ← API Gateway، Async Events
• حدود الأمان: Company Isolation Enforcement
• قاعدة البيانات: PostgreSQL (الجدول الأساسي)
6. 💰 محرك العمولات (Commission Engine)
text
• المسؤولية: حساب وإدارة العمولات
• التقنية: Node.js + Rule Engine
• ملكية البيانات: commissions, commission_rules, payments
• طريقة الاتصال: Async Events ← Message Queue
• حدود الأمان: 
  - Financial Data Integrity
  - Idempotency Enforcement
  - Audit Trail
• قاعدة البيانات: PostgreSQL (الجزء المالي)
7. 📋 نظام المهام (Task Management System)
text
• المسؤولية: إنشاء وتوزيع ومتابعة المهام
• التقنية: Node.js + Workflow Engine
• ملكية البيانات: tasks, task_assignments
• طريقة الاتصال: Sync HTTP ← API Gateway، Async Events
• حدود الأمان: Task Assignment Validation
• قاعدة البيانات: PostgreSQL
8. 🔔 نظام الإشعارات (Notification System)
text
• المسؤولية: إرسال إشعارات عبر قنوات متعددة
• التقنية: Node.js + Queue Workers
• ملكية البيانات: notifications, user_preferences
• طريقة الاتصال: Async Events ← Message Queue
• حدود الأمان: Notification Channel Validation
• التكاملات: Telegram API، Email SMTP
9. 🔗 خدمة التكاملات (Integration Service)
text
• المسؤولية: إدارة التكاملات مع الأنظمة الخارجية
• التقنية: Node.js + Webhook Handlers
• ملكية البيانات: integrations, webhook_logs
• طريقة الاتصال: Webhooks ← External Systems
• حدود الأمان: 
  - HMAC Verification (Shopify)
  - API Key Management
  - Rate Limit Enforcement
• التكاملات: Shopify، Telegram، future payment systems
10. 📊 خدمة التحليلات (Analytics Service)
text
• المسؤولية: تحليل البيانات وتوليد التقارير
• التقنية: Node.js + Elasticsearch
• ملكية البيانات: analytics_data, reports
• طريقة الاتصال: Async Events ← Message Queue، Sync HTTP
• حدود الأمان: Read-only for most users
• قاعدة البيانات: Elasticsearch + PostgreSQL
11. 📜 خدمة التدقيق (Audit Service)
text
• المسؤولية: تسجيل جميع التغييرات على البيانات الحساسة
• التقنية: Node.js + Event Listeners
• ملكية البيانات: audit_logs
• طريقة الاتصال: Async Events ← Message Queue
• حدود الأمان: Immutable Logs
• قاعدة البيانات: PostgreSQL (مع Write-Once policy)
12. 🗄️ قاعدة البيانات الرئيسية (Main Database)
text
• المسؤولية: تخزين البيانات العلائقية
• التقنية: PostgreSQL 15+
• ملكية البيانات: جميع البيانات المهيكلة
• طريقة الاتصال: SQL ← جميع الخدمات
• حدود الأمان:
  - Row-Level Security (RLS)
  - Encryption at Rest
  - Backup & Recovery
• المخطط: حسب وثائق قاعدة البيانات السابقة
13. ⚡ ذاكرة التخزين المؤقت والطابور (Cache & Queue)
text
• المسؤولية: تخزين مؤقت وموازنة الأحمال
• التقنية: Redis 7+
• ملكية البيانات: الجلسات، الطابور، التخزين المؤقت
• طريقة الاتصال: جميع الخدمات
• حدود الأمان: Network Isolation، Authentication
• الاستخدامات:
  - Session Store
  - Message Queue (Bull)
  - Pub/Sub for Events
  - Cache for frequent queries
14. 📁 تخزين الملفات (File Storage)
text
• المسؤولية: تخزين الملفات المرفقة
• التقنية: S3-Compatible Storage
• ملكية البيانات: الملفات، الصور، المستندات
• طريقة الاتصال: HTTPS ← الخدمات
• حدود الأمان: 
  - Signed URLs
  - Access Control Lists
  - Encryption
• الاستخدامات: مرفقات المهام، مستندات العمولات، ملفات الموظفين

🗃️ عرض البيانات والعزل متعدد المستأجرين
إستراتيجية العزل:
text
1. كل جدول يحتوي company_id
2. كل استعلام SQL يضيف WHERE company_id = ?
3. Row-Level Security (RLS) في PostgreSQL
4. API Gateway يضيف company_id من JWT
5. لا JOINs بين شركات مختلفة
تدفق البيانات المالية:
text
1. Shopify Webhook → Integration Service
2. Integration Service → Message Queue (NEW_SALE event)
3. Commission Engine (يستمع للحدث):
   - يتحقق من company_id
   - يحسب العمولة
   - يسجل في PostgreSQL مع company_id
   - ينشر COMMISSION_CREATED event
4. Notification Service (يستمع للحدث):
   - يرسل إشعار للموظف (فقط إذا كان في نفس الشركة)
5. Audit Service (يستمع لكل الأحداث):
   - يسجل التغيير مع company_id
سلامة البيانات المالية:
text
1. الإثباتات غير القابلة للتغيير (Immutable Proofs)
2. سلسلة كتل داخلية (Private Blockchain)
3. توقيعات رقمية لكل عملية
4. سجلات تدقيق شاملة
5. نسخ احتياطية مشفرة
موقع سجلات التدقيق:
text
• الخدمة: Audit Service
• التخزين: PostgreSQL (audit_logs table)
• الهيكل: 
  - company_id (للعزل)
  - user_id (من قام بالإجراء)
  - entity_type (commission, employee, etc.)
  - entity_id
  - action (create, update, delete, approve)
  - old_values / new_values (JSONB)
  - timestamp
• الاحتفاظ: 7 سنوات (للبيانات المالية)

⚠️ مخاطر وفجوات معمارية
الفجوات الحرجة:
1. غياب نظام المصادقة المالية المركزية
text
المشكلة: لا يوجد نظام توقيع رقمي للعمليات المالية
المخاطر: يمكن تزوير العمولات والمدفوعات
الحل: Financial Signing Service مع Private Key لكل شركة
2. غياب نظام البلوكشين الداخلي
text
المشكلة: لا يوجد سجل غير قابل للتغيير للمعاملات المالية
المخاطر: يمكن تعديل السجلات المالية
الحل: Internal Blockchain للعمليات المالية الحساسة
3. نظام الموافقات المتدرجة غير مكتمل
text
المشكلة: الموافقات بسيطة (موافق/غير موافق)
المخاطر: يمكن للمدير الموافقة على أي مبلغ
الحل: Approval Workflow Engine مع حدود مالية
4. غياب نظام كشف الاحتيال
text
المشكلة: لا يوجد تحليل تلقائي للشذوذ
المخاطر: الاحتيال الداخلي قد لا يكتشف
الحل: Fraud Detection System مع Machine Learning
مخاطر الأداء:
1. قاعدة بيانات مركزية واحدة
text
المشكلة: جميع البيانات في PostgreSQL واحدة
المخاطر: نقطة فشل واحدة، صعوبة التوسع
الحل: Database Sharding حسب company_id
2. غياب Read Replicas
text
المشكلة: جميع القراءات على قاعدة البيانات الرئيسية
المخاطر: استعلامات التقارير تبطئ النظام
الحل: Read Replicas للاستعلامات الثقيلة
3. Message Queue كنقطة فشل
text
المشكلة: Redis وحيد للطابور
المخاطر: إذا تعطل Redis، يتوقف النظام
الحل: Redis Cluster مع Replication
مخاطر الأمان:
1. غياب التشفير في Rest
text
المشكلة: البيانات الحساسة مخزنة كنص واضح
المخاطر: إذا اخترقت قاعدة البيانات، تتعرض جميع البيانات
الحل: Column-Level Encryption للبيانات الحساسة
2. غياب Web Application Firewall
text
المشكلة: لا حماية ضد هجمات الويب الشائعة
المخاطر: هجمات SQL Injection، XSS
الحل: WAF أمام API Gateway
3. غياب نظام مراقبة الأمان
text
المشكلة: لا مراقبة للأنشطة المشبوهة
المخاطر: الهجمات قد لا تكتشف
الحل: Security Information and Event Management (SIEM)
مخاطر التوسع:
1. تصميم متعدد المستأجرين بسيط
text
المشكلة: جميع الشركات في نفس قاعدة البيانات
المخاطر: شركة واحدة قد تؤثر على أداء الآخرين
الحل: Database per Tenant للشركات الكبيرة
2. غياب Rate Limiting حسب الخطة
text
المشكلة: نفس Rate Limiting للجميع
المخاطر: الشركات الكبيرة قد تواجه قيوداً
الحل: Tiered Rate Limiting حسب خطة الاشتراك
3. غياب Disaster Recovery Plan واضح
text
المشكلة: لا توجد وثائق لخطة الاستعادة
المخاطر: في حالة كارثة، قد يضيع النظام
الحل: Documented DR Plan مع Recovery Time Objectives
